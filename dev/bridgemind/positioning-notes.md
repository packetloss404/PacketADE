# Positioning Notes

Last updated: 2026-04-09

## Working Thesis

PacketCode should compete as a serious local-first orchestration tool for AI software work, not as a cloud-first product suite.

## Why

BridgeMind's public story is stronger on:

- product suite packaging
- hosted context and account flows
- voice product breadth
- cloud-connected MCP positioning

PacketCode's stronger natural position is elsewhere:

- local project control
- direct terminal-centric workflows
- local memory and orchestration state
- no mandatory hosted dependency for core behavior
- a product shape that feels like an operator tool instead of a SaaS shell

## Product Principles

- core workflows should remain usable without a hosted service
- local state is a feature, not a temporary limitation
- privacy and workspace control should stay visible product advantages
- integrations should enhance local workflows, not replace them
- orchestration quality matters more than marketing surface area

## Practical Implications

- build PacketCode MCP in a local-first way
- prioritize swarm orchestration and file ownership over social or platform features
- avoid copying cloud account mechanics unless they unlock clear workflow value
- treat desktop-native reliability and transparency as part of the product strategy

## What We Are Not Optimizing For

- becoming a bundle of loosely related paid products
- forcing account creation into the core local workflow
- mirroring a cloud-first competitive roadmap feature-for-feature

## Immediate Product Read

PacketCode does not need to beat BridgeMind at being BridgeMind.

PacketCode needs to become the best local-first control plane for multi-agent software execution.
