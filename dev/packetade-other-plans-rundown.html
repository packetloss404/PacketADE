02 - Active plan stack

The non-Remote-Agents tracks

This is the clean planning order after the docs consolidation. Backlog is the live task register; these docs explain why and how.

backlog.md
P1 Remote workspace gap

Sidecar-over-SSH

The sidecar protocol is transport-agnostic. The gap is launching subscription providers against remote codebases by swapping local Node for an SSH-executed sidecar entrypoint.

Next action: design and implement the SSH sidecar launch path in the supervisor.
P2 Workflow polish

Swarm escalation

Roles, ownership, collision checks, and coordination feed are present. The remaining plan is turning blocked work into explicit supervision and reassignment flow.

Next action: define escalation triggers and route them to review/human attention.
P2 Integration layer

PacketADE as MCP provider

PacketADE manages MCP clients today. The deferred plan turns PacketADE itself into a local MCP server exposing flights, tasks, workspaces, review packets, and memory to external tools.

Next action: wait for external-agent demand, then build read-only local server first.
P2/P3 Release readiness

Distribution, updater, quality gates

Local builds are documented across Windows, macOS, and Linux. Updater enablement is blocked on signing keypair, hosted manifest, release assets, and a small UI prompt.

Next action: acquire signing assets and decide release-hosting path.
03 - Mission Planner

Locked v1 design, live runbook, v1.1 backlog

Mission Planner moved PacketADE missions from launch-modal friction to a conversational spec mode with a long-lived planner agent.

mission-planner-plan.md

What shipped

  • One long-lived Claude OAuth planner session per Mission.
  • Spec chat, launch transition, milestones, tasks, journal.
  • Seven real planner tools through in-process MCP.
  • Wake-trigger injection through sidecar protocol v6.
  • Planner/executor cost display and context compaction.

Acceptance runbook

  • Happy path: dark-mode toggle mission populates within ~30 seconds.
  • Stop/restart hygiene keeps mission state recoverable.
  • Approval gate appears for oversized scope.
  • Journal export produces readable markdown.

v1.1 follow-ups

  • Helper planner escalation.
  • Milestone gating and collision detection on async attempts.
  • Crash-resilient planner sessions.
  • Journal incremental fetch and file size caps.
  • Rate-limit and cost-split polish.
Review stance: treat the runbook as the release gate and backlog.md as the live source for open work. The locked design is still required reading before touching Mission Planner internals.
04 - MCP provider

PacketADE as a local context provider

The MCP provider plan is strategically valuable, but deliberately deferred until external agents need PacketADE as a shared local context layer.

mcp-provider-transport.md

Phase 2 local server

Build a localhost HTTP/SSE JSON-RPC server, default port 3100, with read-only resources for project metadata, flights, tasks, memory patterns, workspaces, and pending review packets.

Frontend already done Rust transport deferred

Safe workflow tools

Add low-risk tools after read-only resources: get active flight, list runnable tasks, read task details, append handoff, request review, mark blocked, read memory context, and list workspaces.

Local-only default Per-tool permissions Audit trail required
Good first MCP provider slice
Start with packetade.get_active_project, packetade.list_flights, packetade.get_flight, packetade.list_tasks, and packetade.get_memory_context. That proves external agents can consume PacketADE planning context without scraping local files.

07 - Cost dashboard

Analytics works; alerts are the next user value

The dashboard is implemented and unified around backend analytics. The remaining plan is budget awareness and better attribution.

cost-dashboard-plan.md

Works today

API agent usage, Claude cost tally, and Codex session logs aggregate through read_usage_analytics and analyticsStore.

Known gaps

Mixed cost sources, unknown models pricing to zero, partial per-flight rollup, no caps/alerts, and no per-user attribution.

Recommended next

Add budget thresholds and visible alerts. Decide whether they are global, per-provider, per-flight, or all three.

08 - Release operations

Builds are documented; signing is the blocker

Release readiness is now mostly an operations track: native build runbooks, signing credentials, updater manifest hosting, and local checks.

multi-platform-build.md

Multi-platform builds

  • Windows x64: EXE plus NSIS installer.
  • macOS x64/ARM64: app plus DMG.
  • Linux x64/ARM64: AppImage plus DEB.
  • Node 24.15.0 sidecar runtime fetched per target triple.

Updater runbook

  • Tauri updater is not enabled today.
  • Use full-installer updates, not diff patches.
  • Requires signing keypair, HTTPS manifest, release assets, and UI prompt.
  • Keep private key offline.

Local quality gates

  • pnpm preflight for fast confidence.
  • pnpm check for release confidence.
  • Includes Playwright, sidecar checks, schema validation, Rust check/tests.
  • No GitHub Actions CI is expected.
09 - Sidecar reference

The sidecar is a shipped foundation, not a fresh plan

The Node sidecar is the bridge for subscription providers, OpenAI Agents SDK, Mission Planner, and the normalized api-agent:* event vocabulary.

agent-sidecar/README.md

Providers

Echo, Claude OAuth, OpenAI Codex, and OpenAI Agents SDK are routed through the sidecar; API-key providers mostly run in Rust.

Protocol v6

v6 adds typed rate_limited events for Mission Planner quota pause. Earlier versions added model switching, retry, attachments, edits, cancel-pending-tools, and wake-trigger injection.

Bundling

Production builds package the sidecar, pruned production dependencies, and pinned Node runtime as Tauri resources/external binary.
