01 - Executive snapshot

What we are building

Remote Agents turns the desktop app into an online agent host that a signed-in phone can safely control through Packet Cloud.

01-product-scope.md

Product promise

All PacketBench agents, providers, models, profiles, workspaces, and approvals from a phone while secrets and tools stay on desktop.

Primary mental model

"My desktop PacketBench is an online agent host. My phone signs into Packet Cloud and controls that host."

Success shape

Start or continue API-agent conversations, stream events, approve prompts, cancel, retry, and recover after reconnect.

The defining boundary: Packet Cloud routes and audits. It does not call OpenAI, Anthropic, Ollama, MCP servers, local files, SSH, or shell tools. The desktop remains the execution authority.
02 - Product shape

MVP, non-goals, and user journeys

The MVP is intentionally narrow enough to ship, test, and secure. It is not a cloud coding environment and not remote desktop.

Scope doc

MVP includes

  • Packet account sign-in on desktop and PWA.
  • Desktop "Enable Remote Agents" switch and host registration.
  • Mobile device registration, approval, and revocation.
  • Host, workspace, provider/model, profile, and conversation discovery.
  • New and continued API-agent conversations from the phone.
  • Streaming api-agent:* events and compact mobile cards.
  • Permission and pending-edit approval flows.
  • Web Push for needs-approval, finished, and failed states.
  • Remote command audit trail for every mutating action.

MVP excludes

  • Native iOS/TestFlight build.
  • Raw PTY sessions or full mobile terminal control.
  • Full file browser/editor and broad remote deploy controls.
  • Running agents in cloud without desktop online.
  • Cloud-stored provider API keys or OAuth tokens.
  • Team/org sharing, billing plans, and cloud runner mode.
  • QR as the primary identity or pairing model.

First-time setup

Enable Remote Agents in desktop, sign into Packet Cloud, register host, sign into PWA, request access, approve on desktop, open host dashboard.

Start from phone

Pick host, workspace, profile, provider/model, and mode. PWA sends conversation.start; desktop creates a first-class session.

Approve while away

Desktop emits the existing permission event, relay forwards it, push wakes the user, and mobile sends a narrow approval response.

04 - Architecture

Desktop-owned execution through a cloud relay

The standalone Rust service at D:\projects\packetrelay is the default. PostgreSQL owns durable identity, ticket, replay, audit, and outbox state while the protocol remains hosting-provider-neutral.

02-architecture.md

Mobile PWA

Signs in, stores device key and cursors, sends commands, renders streams.

Rust Relay API

Auth, metadata routes, WebSocket tickets, push subscriptions.

Host-room router

One in-process room per desktop host; routes commands/events while PostgreSQL stores replay.

Desktop Gateway

Outbound socket, host registration, device trust, command validation.

PacketBench Runtime

API agents, sidecar providers, keyring, OAuth, MCP, local/SSH tools.

Cloud owns

  • Account, host, device, ACL metadata.
  • Encrypted PostgreSQL replay buffer and vendor-neutral artifact references.
  • Audit rows, rate limits, revocation, push jobs.

Desktop owns

  • Provider secrets, OAuth files, keyring credentials.
  • Conversation creation, persistence, approvals, local events.
  • Local files, SSH workspaces, MCP env/config, shell tools.

PWA owns

  • Device private key and auth session.
  • Last-seen cursors, cached summaries, drafts, outbox.
  • Mobile-friendly reducers and reconnect behavior.
Key desktop refactor: create a backend RemoteConversationService so phone-created conversations become first-class desktop conversations instead of being owned only by React store state.
05 - Protocol

Narrow, versioned, auditable envelopes

The relay sees routing metadata only. Prompts, transcripts, tool inputs, diffs, local paths where possible, and approval details move inside encrypted payloads before external beta.

03-protocol.md

Allowed command surface

  • List hosts, workspaces, providers, models, profiles, conversations.
  • Start, continue, cancel, retry, close, and change model for API-agent conversations.
  • Stream existing api-agent:* events as wrapped agent.event payloads.
  • Respond to permission requests and pending edits.
  • Cancel pending tools and observe cost/status summaries.

Explicitly forbidden by default

  • No raw Tauri invoke bridge.
  • No raw PTY control in v1.
  • No cloud-side provider secrets.
  • No arbitrary shell command submission outside agent permission flow.
  • No mobile allow_always until step-up auth and stronger risk UI exist. 
RemoteEnvelopeV1:
  v, envelopeId, traceId, accountId, hostId, deviceId
  channel, type, streamId, seq, ack, idempotencyKey
  createdAt, ttlMs, keyId, ciphertext, signature

Production rule:
  agent, approval, file, and control payloads require ciphertext + signature.

Sequencing

The Rust host router assigns monotonic event sequence numbers per host and conversation and persists replay before acknowledgement. PWA resumes with its last processed cursor.

Idempotency

Mutating device commands carry an idempotency key; desktop keeps a processed-command cache to avoid duplicate prompts.

Snapshots

Provider, workspace, profile, and conversation snapshots are generated by desktop; the PWA does not duplicate provider catalogs.

06 - Security

High-risk infrastructure from day one

Remote Agents controls an agent that can read, write, run commands, use API credentials, and call MCP tools. The security design treats that as the central fact, not an edge case.

04-security.md

Identity

  • Passkey-first Packet account sign-in.
  • Magic-link or one-time email fallback.
  • Desktop sign-in via browser PKCE, no embedded client secret.
  • Short-lived WebSocket tickets minted by HTTPS control plane.

Device trust

  • Account sign-in alone is not enough for host control.
  • Desktop approves each new mobile device in v1.
  • Trust grant binds account, host, device, public keys, scopes.
  • Revocation closes active sockets and fails future commands closed.

Payload privacy

  • TLS is not sufficient for external beta.
  • Use audited HPKE or Noise-based session transport.
  • Relay buffers ciphertext only for sensitive channels.
  • No custom crypto beyond composition, AAD, sequence, nonce rules.

Private beta launch gate

  • Real account auth and device approval/revocation.
  • Object-level authorization tests.
  • WebSocket origin validation and rate limits.
  • Audit log for mutating commands.
  • E2EE test vectors pass in Rust and browser.
  • Revoked active device loses WebSocket within 5 seconds.
  • Cloud logs scan clean for prompt/tool content.

Provider secret isolation

The PWA can receive auth status such as ready, login_required, missing_key, or service_down. It must never receive API keys, OAuth files, MCP environment variables, SSH private keys, local env vars, or raw shell profile data.

07 - PWA

Mobile as intent and decision surface

The PWA should open directly into work after sign-in. It is a compact agent-control surface, not a marketing site and not a terminal wall.

05-pwa.md

Needs Me

Approvals, pending edits, failed runs, blocked conversations.

Active

Running conversations grouped by host and workspace.

New

Host, workspace, profile, provider, model, mode, prompt.

History and Hosts

Completed conversations, host status, trusted devices, settings.

Conversation cards

  • User message and assistant text.
  • Thinking collapsed by default.
  • Tool start/result cards.
  • Permission and pending-edit cards.
  • Plan block, token/cost summary, done/error.
  • Cancel, retry, model, approvals, and context toolbar.

Reconnect and push

  • Foreground updates use WebSocket.
  • Push only wakes the user for attention-needed events.
  • iOS push requires installed Home Screen PWA.
  • Reconnect sends resume.request with per-conversation cursors.
  • If replay is missing, PWA asks host for a fresh snapshot.
08 - Implementation plan

Seven checkpoints to private beta

Sprints are written as checkpoints, not calendar promises. Sprint 0 and Sprint 1 can start in parallel once the six-agent team is assigned.

06-implementation-plan.md
Sprint 0

Foundations and decisions

Protocol schemas, repo layout, feature flag, PWA/Rust-relay skeletons, auth/encryption decisions.

Checkpoint: shared protocol, packet-relay, PWA, and desktop feature flag all build.
Sprint 1

Relay and host presence

Desktop and PWA connect to relay and see host online/offline state.

Checkpoint: phone sees desktop online; unauthorized device cannot subscribe.
Sprint 2

Provider, workspace, profile snapshots

Phone can see what desktop can run without leaking secrets.

Checkpoint: PWA picker mirrors desktop auth/model/workspace state.
Sprint 3

Backend conversation service

Phone-created conversations become first-class PacketBench conversations.

Checkpoint: stream appears on desktop and PWA; cancel from PWA stops run.
Sprint 4

Mobile conversation UX

Needs Me, Active, New Agent, chat cards, approvals, replay, IndexedDB cursors/drafts.

Checkpoint: phone lock/reopen resumes stream; approval unblocks desktop agent.
Sprint 5

Push, audit, security hardening

Web Push, audit log, rate limits, revocation, desktop device UI, encryption gate.

Checkpoint: revocation kills active socket; every mutating command is audited.
Sprint 6

Beta polish and release

Generated protocol docs, load test, mobile matrix, failure runbook, staged deploy.

Checkpoint: 30-minute remote session with disconnects passes on iOS and Android.

10 - Testing

Correctness, security, and mobile reliability

The test plan is shaped around three failure classes: duplicated/lost agent state, unauthorized or leaky remote control, and unreliable mobile reconnect/push behavior.

08-testing.md

Unit and contract

  • Shared protocol parses valid frames and rejects unknown versions.
  • Mutating commands require idempotency keys.
  • Rust relay ACL, origin validation, rate limits, audit rows.
  • Desktop validates commands and redacts snapshots.
  • PWA reducers dedupe events and expire outbox TTL.

Integration and E2E

  • Fake PWA to packet-relay dev to fake desktop harness.
  • Real desktop with fake provider for deterministic streams.
  • Desktop plus PWA: start, stream, follow-up, approval, cancel.
  • Playwright mobile viewports for host list, chat, approval, reconnect.

Security and load

  • Cross-account, revoked, expired, bad-origin, mismatched-host tests.
  • Provider secrets, SSH key paths, MCP env values absent from logs/snapshots.
  • 1,000 idle hosts, 100 active streams, slow client, reconnect storm.
  • iOS/Android installed PWA and browser-tab manual matrix.
Acceptance test in one paragraph
A user with PacketBench desktop running on Windows signs into Packet Cloud, enables Remote Agents, opens the PWA on iPhone, signs in, requests access, approves on desktop, starts an api-openai-codex or api-claude-oauth conversation against D:\projects\PacketBench, receives streaming output, approves one risky tool, cancels or completes the run, and then opens the same conversation on desktop.
11 - Open decisions

What still needs an owner call

Several product-shaping choices are locked. A few implementation choices should be decided during Sprint 0 or by the named owner.

09-open-decisions.md

Locked

  • Cloud sign-in is primary; QR is not the primary pairing model.
  • Desktop PacketBench owns execution and secrets.
  • PWA first; native iOS/TestFlight later.
  • API agents only in MVP.
  • WebSocket relay for foreground control; Web Push for notifications.
  • The standalone Rust packet-relay service is the selected implementation.

Still open

  • Auth provider: build passkey/magic link or use Clerk/Auth0/Stytch/Supabase.
  • Encryption timing details: exact internal-dev to private-beta gate.
  • Code location finalization under remoteagents/ or app workspace.
  • Backend conversation persistence shape for MVP vs post-MVP.
  • Native iOS strategy after PWA beta.
12 - Owner review

Questions to answer before kickoff

This is the practical checklist for reviewing the plan before handing it to a six-agent implementation team.

Runbook
Do we accept PWA-first as the only MVP mobile target?

Native iOS/TestFlight waits until relay, auth, push, and UX prove useful.

Do we want an auth vendor for private beta?

Passkeys plus magic-link fallback are preferred; username/password should stay out unless unavoidable.

Is E2EE a hard external-beta gate?

The docs say yes. Internal plaintext can move fast, but external users require encrypted agent/approval/file frames.

Are we comfortable excluding raw PTY from v1?

This keeps scope and risk manageable while still delivering the core remote-agent loop.

Can Sprint 3 own the backend conversation refactor?

This is the main product architecture risk. Without it, phone-created runs will feel bolted on.

What is the first demo?

The clean demo is a trusted PWA seeing desktop online, then starting a real API-agent conversation and approving one prompt.
