User Guide

PacketADE Manual

How to install PacketADE, wire up your providers, and run real development work through Workspaces, Agents, and the Flight Deck. Task-oriented where possible, honest about limits everywhere.

v0.10.2 Apache 2.0 Tauri v2 · React 19 · Rust · Node sidecar Local-first · BYOK
Chapter 01

Getting Started

Install the app, authenticate at least one provider, open a folder, and start your first session. Everything else in this manual builds on the pieces you set up here.

What is PacketADE?

PacketADE is a local-first desktop Agent Development Environment: a single native app for running and supervising AI software work. It connects two complementary execution styles:

  • PTY-backed CLI sessions — real terminals in draggable workspace mosaics, running Claude Code, Codex CLI, OpenCode, PacketCode, or a plain shell.
  • GUI/API agent conversations — durable structured chats in the Agents view with streaming, tool calls, permission gating, inline diffs, plans, review, and git worktree endings. Eight provider rows: Anthropic subscription and API, OpenAI ChatGPT/API/Agents SDK, MiniMax, OpenRouter, and local Ollama.

Above the sessions sit the organizing surfaces: Flights (units of delegated work on the Flight Deck), an Issues kanban board with AI spec import, a project Memory layer, git-host integration (GitHub plus self-hosted Gitea/Forgejo), an MCP hub, SSH remotes, local Whisper dictation, and cross-provider cost tracking.

Everything stays on your machine: API keys in the OS keyring, conversations and history under ~/.packetade, execution on your hardware (or your SSH hosts). There is no PacketADE cloud service and no telemetry.

Naming notes. This product was previously called PacketCode; that name now belongs to a separate terminal (TUI) coding agent that PacketADE detects and treats as its recommended workspace CLI. You may also see the word "Mission" in very old data — the current term for a unit of work is Flight, managed on the Flight Deck.

Install & first run

Option 1 — Download a release

Grab the latest installer from the GitHub Releases page, run it, and open PacketADE.

Builds are currently unsigned. Windows Authenticode signing, macOS notarization, and the auto-updater are planned but blocked on code-signing certificates. Expect a SmartScreen or Gatekeeper warning on first launch, and install updates manually.

Option 2 — Build from source

Prerequisites: Node.js, pnpm, a Rust toolchain, and the Tauri OS toolchain for your platform (VS Build Tools on Windows, Xcode CLT on macOS, GTK/WebKit dev packages on Linux).

git clone https://github.com/packetloss404/PacketADE.git
cd PacketADE
pnpm install
pnpm tauri dev      # hot-reload dev mode
pnpm tauri build    # production build (also fetches Node + builds the sidecar)

The first build compiles the Rust backend and the Node agent sidecar — expect several minutes. On Windows, the Rust stable toolchain's bin directory must be on PATH (e.g. %USERPROFILE%\.rustup\toolchains\stable-x86_64-pc-windows-msvc\bin).

Your first workspace

PacketADE opens to a Welcome screen when nothing is active.

  1. Click New Workspace (also available from the toolbar's folder picker).
  2. Pick a project folder — from the OS picker or the recents list.
  3. Save. The workspace opens with an empty mosaic and a session picker.
  4. Pick a CLI from the picker (Terminal always works; installed CLIs are detected automatically) — a live PTY pane appears.

Workspaces remember their panes, layout, and settings across restarts. A workspace can also be bound to an SSH server, in which case its sessions run on the remote host (see Connect an SSH server).

Finding your way around

The left rail pins six views — Workspace, Agents, Flight Deck, Issues, Memory, GitHub — with the Settings gear at the bottom. Three more surfaces (Session History, Cost Dashboard, Dictation) are reached from the command palette, keyboard shortcuts, the toolbar mic button, or the status strip's live-spend chip.

  • Ctrl+K opens the command palette — views, prompt templates, and tool modules, all searchable.
  • Ctrl+Shift+W Workspace · Ctrl+Shift+1 Agents · Ctrl+Shift+2 Flight Deck. Full list in the shortcut reference.
  • The status strip along the bottom shows the current view, running agents, live session spend, and a sidecar health chip when the sidecar is unhealthy.
Five-minute tour: authenticate one provider, open a workspace at a real repo, launch a Claude Code pane and ask it to explain the codebase. Then open Agents (Ctrl+Shift+1) and start a structured conversation with the same provider to see the GUI-agent side: streaming, tool cards, and inline diffs.
Chapter 02

Core Concepts

Seven ideas explain almost everything in PacketADE. Read this chapter once and the rest of the app becomes predictable.

Workspaces

A workspace is a project workroom: a folder (local or on an SSH host) plus a persistent mosaic of terminal panes. Workspaces are deliberately CLI-first — the session picker offers only PTY sessions (Terminal, Claude Code, Codex CLI, OpenCode, PacketCode). Structured GUI-agent conversations are created in the Agents view, not here; older saved layouts that contain conversation panes still load for compatibility.

Each pane is a real terminal driven by the CLI's own UI. PacketADE adds status bars for the CLIs it understands (Claude, Codex, OpenCode), install detection with recovery hints, and — when PacketCode is installed — marks it as the recommended CLI. Panes, models, and toggles are remembered per workspace.

The workspace header also hosts the Git dashboard slide-out: branch state, and the worktree lifecycle actions for conversations that ended with pending work (see Git endings).

Agents conversations

The Agents view owns GUI-agent work: creating conversations, the cross-project conversation and attention list, one large active conversation, and its inspector. A conversation is a durable, structured thread with an API or subscription provider.

Two backends serve these conversations behind one event contract: most API-key providers run in-process in Rust; the two subscription providers and the OpenAI Agents SDK run in a bundled Node sidecar. The frontend cannot tell the difference, and neither will you — every conversation gets the same streaming, tool cards, permission prompts, per-hunk diff acceptance, plan panel, and cost accounting.

Key mechanics:

  • Modes — a single chip cycles default / plan / manual / deny / yolo with Shift+Tab. Plan mode keeps the model read-only until you approve its proposed plan inline; manual asks before risky tools; deny blocks all writes; yolo skips permission prompts. Providers that can't pause for approvals (Codex exec) show only three honest sandbox postures instead: Read-only, Workspace-write, and Full access.
  • Pending edits — file writes arrive as reviewable diffs. Accept whole files or individual hunks; batch "Apply all / Reject all" rollups appear when 2+ prompts stack up.
  • Worktree endings — a conversation that wrote code can hand off to git explicitly: the ReviewBar's Finish flow opens the workspace git panel scoped to that conversation's worktree, with Merge back / Create PR / Discard / Keep.
  • Extras — slash commands, @-file mentions, image attachments (drag or paste, 5 MB cap), a Side Chat overlay for side questions, inline transcript restore (rewind), and a /review reviewer subagent that critiques pending writes.

Flights & the Flight Deck

A Flight is the top-level unit of work — above issues and sessions. The Flight Deck is its single-screen master-detail control surface: flight list on the left, detail (attempts, plan, coordination, output review, cost) on the right.

A flight can carry an upfront plan (milestones and tasks, produced by the planning conversation) and any number of attempts. An attempt is one agent executing against the flight's objective in its own git worktree and branch — on your machine or an SSH host. Because attempts are isolated, you can launch several in parallel (different agents, different hosts) and compare the results.

Two important honesty notes:

  • Attempts are user-launched. The plan structures the work; it does not autonomously schedule executors. (An earlier autonomous planner was intentionally removed.)
  • Flights link bidirectionally to Issues and can roll up token costs from their attempts.

Issues

The Issues view is a kanban board with nine statuses (Backlog, Up Next, To Do, In Progress, In Review, QA, Done, Blocked, Needs Human), priorities, labels, epics, and acceptance criteria. Two features distinguish it from a plain board:

  • Spec import — paste a spec or feature description into Import Spec; Claude decomposes it into editable ticket drafts you accept into the backlog.
  • Send to Workspace — an issue can be handed to a workspace session, and commit trailers (Fixes #N) close the loop back to the board.

Memory

The Memory view keeps project context that outlives individual conversations, in four tabs: Patterns (learned, deduplicated observations), Timeline (auto-captured events), Project notes (manual), and Ask (query your memory). Memory can be exported as JSON or a Markdown digest, imported, filtered by flight or project, and cleared.

In an Agents conversation, a header memory toggle controls whether memory context is injected into the system prompt — its tooltip previews exactly what would be injected.

The MCP hub

PacketADE is both an MCP client and an MCP server:

  • Client — configure MCP servers at global or project scope; conversations expose an N/M header dropdown to toggle which servers a given conversation may use.
  • Provider — PacketADE can serve its own flights, tasks, and memory as MCP resources to external clients (default port 3100). It is strictly read-only unless you explicitly enable the append-only handoff write tool.

SSH remotes

A server record (name, host, port, user, auth method) is the single SSH identity used everywhere: remote workspace PTY sessions, API-agent file/bash tools running against remote code, and remote flight attempts with remote worktrees. Auth methods are SSH agent, key file, or password (passwords go in the OS keyring). Host-key fingerprint pinning is enforced: PacketADE records a server's fingerprint and refuses flight launches against servers without one.

Chapter 03

How-To Guides

Recipes for the workflows you'll actually run, in roughly the order you'll meet them.

Launch a CLI session

  1. Open the Workspace view (Ctrl+Shift+W) with an active workspace.
  2. Click Add Session in the workspace header (or use the inline picker in an empty workspace).
  3. Pick one of the five session types: Terminal, Claude Code, Codex CLI, OpenCode, or PacketCode. Uninstalled CLIs show an install hint; PacketCode shows a guided setup link. For SSH-bound workspaces, availability reflects what's installed on the remote host.
  4. The pane spawns with the CLI live. Drag panes to rearrange the mosaic; panes persist across view switches and app restarts.
Gemini CLI support was removed. Saved layouts that contained a Gemini pane load as plain Terminal panes. On Windows, PacketADE resolves .cmd wrappers (claude.cmd, codex.cmd, …) automatically.

Start an API-agent conversation

  1. Open Agents (Ctrl+Shift+1).
  2. In the launcher, pick a provider row — eight rows grouped by vendor, each with a live auth badge. Pick a model, an optional agent profile, and a project.
  3. Optionally set the mode chip (Shift+Tab cycles default / plan / manual / deny / yolo; Codex shows sandbox postures instead) and attach images (drag-drop or paste, 5 MB each).
  4. Type your prompt — use / for commands and saved templates, @ to mention files — and send.

During the run you'll see streamed text, thinking indicators, tool cards with outputs, permission prompts (unless yolo), and pending-edit diffs you can accept per hunk. The header shows model, context-percent gauge, cumulative tokens, session cost, and git branch. When writes settle, use the ReviewBar to review everything, then Finish → Commit… to open the git ending surface.

Ctrl+N starts a new conversation while you're in Agents.

Plan a Flight (Option B planning)

Flight planning is an ordinary read-only agent conversation that produces a structured plan you explicitly apply. Nothing runs autonomously.

  1. On the Flight Deck (Ctrl+Shift+2), click New Flight (or the toolbar's + New → New Flight).
  2. In the launch modal, describe the objective, select an agent, and click Plan first instead of launching.
  3. PacketADE starts a planning conversation restricted to read-only tools (read_file, list_directory, grep). Refine the plan conversationally — the agent explores the repo and emits its plan as a fenced packetade-flight-plan JSON block (up to 12 milestones, each with tasks, dependencies, owned paths, and validation criteria).
  4. Back on the flight's detail pane, the Planning card parses the latest plan block. Click Apply latest plan (or Replace with latest) to materialize milestones and tasks onto the flight.
  5. Launch attempts whenever you're ready — planning and execution are separate, deliberate steps. Reopen the plan conversation anytime via Open plan.

Launch parallel worktree attempts

  1. From the Flight Deck, open the launch modal — New Flight for a fresh flight or Launch attempt on an existing one.
  2. Pick one or more targets: your local machine and/or configured SSH servers, each paired with an agent. One attempt is created per target, each in its own git worktree and branch, so they can't collide.
  3. Optional toggles: publish attempts as draft PRs (auto-push + draft PR on clean completion — requires a repo connected in the GitHub view) and an independent reviewer gate with its own reviewer agent.
  4. Press Ctrl+Enter to launch.

Attempts progress through queued → provisioning → running → reviewing → completed (or failed / cancelled). While an attempt runs you can send it follow-up messages from its tile composer, open a read-only Monitor window, or open its worktree in a full Workspace.

SSH targets require a pinned host key. Launches against servers without a recorded fingerprint are blocked. Re-run the server's connection test in Remote Hosts settings to capture one.

Review & publish an attempt

  1. When an attempt reaches reviewing, open its tile on the flight detail pane. The Output review card summarizes reported files and owned paths across the flight's tasks.
  2. If the reviewer gate is enabled, its verdict appears on the tile: pass, changes_requested, or blocked, with findings. You can retry the gate, send findings to the builder agent as a follow-up turn, or override the gate with a written reason.
  3. To inspect the actual changes, click Open in Workspace — the attempt's worktree opens in a CLI-first workspace where you can diff, test, and edit.
  4. Mark the attempt completed. If the flight has draft-PR publishing enabled, PacketADE pushes the attempt branch and opens a draft PR at that moment (while the worktree still exists). Publish failures are recorded on the attempt without failing it.
  5. Losing attempts can be marked cancelled or discarded; their worktrees are independent, so dropping one never affects another.

Connect an SSH server

  1. Open Settings → Workspaces & Terminal → Remote Hosts and click Add Server.
  2. Enter name, host, port, username, and an auth method: SSH agent, key file (path to a private key), or password. Passwords are stored in the OS keyring, and password-auth servers prompt at connect time.
  3. Run the connection test. It walks through connect/auth steps, records the host-key fingerprint for pinning, and detects which agent CLIs are installed on the host.
  4. Use the server anywhere: bind a workspace to it (remote PTY sessions), point an Agents conversation at a remote project (remote file/bash tools), or select it as a flight-attempt target (remote worktrees).

Without a pinned fingerprint, connections fall back to trust-on-first-use with a logged warning — and flight launches are blocked entirely. Prefer re-testing the connection to capture the fingerprint.

Configure MCP

Servers PacketADE connects to

  1. Open Settings → Integrations & Data → MCP.
  2. Add a server at global or project scope. Diagnostics on each entry show connection health.
  3. In any Agents conversation, use the header N/M MCP dropdown to toggle which servers that conversation may use. Remote (SSH) conversations receive their MCP configuration over the wire as well.

PacketADE as an MCP server

Enable the provider in the same settings section to expose flights, tasks, and memory as MCP resources on port 3100 (configurable). Choose project or global scope, restrict the allowed tool list, and — only if you need external agents to write handoffs — enable the append-only write tool. Everything else stays read-only.

Use dictation

Dictation is fully local: audio is transcribed on-device by Whisper. Nothing leaves your machine.

  1. Open the Dictation view via the toolbar mic button or Ctrl+Shift+D.
  2. Download a Whisper model (sizes trade speed for accuracy) and pick your input device in Settings → Integrations & Data → Dictation.
  3. Record: push-to-talk (hold Ctrl+Alt+Space — release to transcribe and auto-paste) or toggle (Ctrl+Alt+R). Esc cancels a recording.

Notes: OS-global shortcuts are an explicit opt-in (both shortcuts are re-bindable); transcripts auto-paste into the focused PacketADE field, with an optional system-wide paste into whatever app is foregrounded; a custom dictionary biases transcription toward your jargon; language can be fixed or auto-detected; recordings are capped (configurable, 10–1800 s). The view also keeps a history with analytics — WPM, streaks, top words.

Track costs

Every API-agent turn reports token usage, and PacketADE rolls it up in three places:

  • In the conversation — the tile header shows cumulative tokens and session dollars live; /usage jumps to the dashboard.
  • The Cost Dashboard — open it from the status strip's live-spend chip. Filter by source/provider, scan daily spend bars and the per-model usage table (cache-aware token columns), and set a monthly overall limit plus per-provider limits.
  • Per flight — attempts roll token costs up onto their flight, so a flight's detail pane answers "what did this piece of work cost?" across every agent that touched it.

Subscription-provider sessions (Claude OAuth, ChatGPT) don't bill per token; their usage still appears in the roll-ups but costs your subscription, not your API budget.

Chapter 04

Troubleshooting

The failure modes you're most likely to hit, what they mean, and the shortest path out.

Auth badges

BadgeMeaningFix
readyProvider is usable now.—
login_requiredOAuth credentials missing or expired with no refresh token.Click Log in on the row (opens a one-shot claude login / codex login terminal) or run the login in any terminal. The badge updates automatically when the credential file changes.
missing_keyNo API key in the OS keyring for this provider.Add the key under Settings → Agents & Models → Providers & Models.
service_downThe provider's local service isn't reachable — for Ollama, the daemon isn't answering on localhost:11434.Start the service (e.g. launch Ollama) and re-check.
coming_soonProvider row exists but isn't wired up.—
An expired access token is not a problem. If a refresh token is present, the badge stays ready ("Session will auto-refresh on next use") — the SDK/CLI refreshes transparently. Don't re-login just because a token's expiry date has passed.

Sidecar status

Subscription providers and the OpenAI Agents SDK run in a supervised Node sidecar. When it's healthy the status chip is hidden; you'll only see it when something is wrong:

ChipMeaningFix
sidecar restarting (n/3)The sidecar process exited and the supervisor is relaunching it (up to 3 tries). The tooltip carries the last error.Usually self-heals. If it keeps cycling, check the tooltip's error.
sidecar downRestart budget exhausted; sidecar-backed providers are unavailable. In-process providers (Claude API, OpenAI API, MiniMax, OpenRouter, Ollama) keep working.Restart the app. In dev, ensure agent-sidecar/dist/index.js is built and node is on PATH; the env vars PACKETADE_SIDECAR_PATH / PACKETADE_NODE_PATH override entry-point resolution.

A protocol-version mismatch between the app and the sidecar logs a warning but is non-fatal.

Attempt failures

A failed attempt carries a structured failure category:

CategoryLikely cause / fix
authProvider credentials invalid on the machine that ran the attempt — re-login or fix the key (remember: SSH attempts use the remote host's CLI auth).
billingProvider account out of credit or plan limits.
rate_limitProvider throttling — wait or spread attempts across providers.
context_overflowThe task blew past the model's context window — split the flight into smaller tasks or use a larger-context model.
timeout / server_errorTransient provider or network trouble — relaunch the attempt.
not_installedThe selected agent CLI isn't installed on the target — install it, or re-run the server's connection test to refresh detection.
unknownUncategorized — read the attempt's error output.

Git endings & publish

  • "Nothing to land" on Merge back — the conversation branch has no changes to merge; Discard it if you're done.
  • Discard requires an explicit confirm when the worktree is dirty. There is deliberately no silent path that drops uncommitted work.
  • Merge back is disabled for SSH conversations — merge remotely from a shell, or use Create PR.
  • "Draft-PR publish skipped: no GitHub repo selected" — connect and select a repo in the GitHub view; publishing pushes the branch and calls the host's PR API. Similar messages distinguish push failures from PR-creation failures.
  • Publish never fails the attempt — a failed publish is recorded as an error message on the attempt; the work in the worktree is untouched.

Other common issues

  • GitHub asks you to reconnect after every restart. By design: the git-host token is held in backend memory only and is not persisted.
  • SmartScreen / Gatekeeper blocks the installer. Builds are unsigned until code-signing certificates land; "Run anyway" / right-click-Open is currently the expected path.
  • A flight launch is blocked on an SSH server. The server has no pinned host fingerprint — re-run its connection test.
  • Dictation global shortcuts don't fire. They're an explicit opt-in toggle in Dictation settings; also check the shortcut hasn't been claimed by another app.
  • Data from an old PacketCode install. On first boot PacketADE migrates ~/.packetcode → ~/.packetade, legacy keyring entries, and packetcode:* localStorage keys automatically.
  • Old view shortcuts changed? The number-row chords map by shifted character (Shift+1 = !), so non-US keyboard layouts can shift which number triggers which view. This is a known caveat.

Event channels

All AI streaming uses feature-scoped Tauri events. The API-agent contract is api-agent:{kind}:{sessionId} where kind is one of:

chunk · thinking · thinking-stop · tool-start · tool-result
permission-request · pending-edit · edit-baseline · plan-block
tool-output-extended · turn-summary · mcp-sources · done · error

Both backends (in-process Rust and the Node sidecar) emit this exact shape. Global app events: provider-auth:changed (auth badge refresh) and sidecar-status:changed (health chip). Other features use their own scopes, e.g. insights:chunk, side-chat:chunk. The sidecar's stdio protocol is newline-delimited JSON, currently protocol version 11.

Data locations

~/.packetade
Persistent app data: conversations, checkpoints, slash commands, usage logs, dictation history, and more. A legacy ~/.packetcode directory is migrated once on startup.
OS keyring
Service packetade: provider API keys and SSH passwords (ssh-<serverId> entries). Legacy packetcode entries are read and migrated.
Log directory
%APPDATA%\PacketADE on Windows; ~/Library/Application Support/PacketADE on macOS.
localStorage
UI store persistence under the packetade:* prefix (legacy packetcode:* keys read only for migration).
~/.claude, ~/.codex
OAuth credentials owned by the Claude Code / Codex CLIs. PacketADE watches them but never writes them.
Git-host token
Backend memory only — not persisted; reconnect after each app restart.
